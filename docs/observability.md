# Operational observability

FND-07 adds a small, privacy-bounded way to answer two questions: "can the process serve HTTP?" and "is it currently safe to depend on the service?" It also adds structured events that can be read through the service's stdout/stderr destination, such as systemd's journal.

It does not add Prometheus, an external monitoring service, an application log viewer, or public health endpoints.

## Private HTTP endpoints

All endpoints use the existing listener bound only to the discovered `tailscale0` IPv4 address. They are not served on localhost, a wildcard address, or the public network by production code.

| Endpoint | Meaning | Status code |
| --- | --- | --- |
| `GET /api/v1/health/live` | The process is alive enough to serve this request. | Always `200` when a response is possible. |
| `GET /api/v1/health/ready` | Required configuration and history storage are usable and maintenance mode is off. | `200` when ready; otherwise `503`. |
| `GET /api/v1/health` | Compatibility alias for readiness. | Same as readiness. |
| `GET /api/v1/status` | Current bounded operational snapshot. | `200` for a valid snapshot. |

`HEAD` is supported with the same status and headers but no response body. Other methods return a versioned `405` API error.

Liveness deliberately does not inspect dependencies: a live process can still be not ready. Readiness fails closed when configuration is unavailable, history storage is unavailable, or maintenance mode is active. These conditions would make current monitoring unsafe or misleading.

Audit storage is optional for read-only startup, so its failure produces `degraded` status rather than failed readiness. It will prevent future state-changing actions. Using a protected previous configuration, a collector failure, or Docker failure also degrades status without claiming that the HTTP service itself is unusable.

## Status fields and honest placeholders

`/api/v1/status` reports:

- overall state and process uptime;
- maintenance and configuration state;
- history and audit database availability;
- database size in bytes when the database, WAL, and shared-memory files can be inspected safely;
- whether collection is running, the last completed run, and the last successful completion time;
- backup state and Docker connectivity.

Database paths are never returned. A size is `null` if the base file is missing, is a symlink, is not a regular file, or cannot be read. Optional WAL and shared-memory files are included when present.

The production scheduler is now active and reports its real run state. Until their later roadmap tasks are implemented, Docker collection fails explicitly with `docker_not_implemented`, Docker connectivity remains `not_checked`, and backup state remains `not_implemented`. These values are deliberate evidence of unfinished work, not successful checks.

## Request correlation

Every request receives a new opaque request ID generated by the server. The same ID appears in:

- the `X-Request-ID` response header;
- the versioned JSON response envelope;
- the request context available to backend handlers;
- the corresponding structured request log.

An incoming `X-Request-ID` header is discarded. This prevents a client from choosing misleading or unsafe log correlation values.

## Structured log schema

Each log line is one JSON object. Informational events go to stdout; warning and error events go to stderr. Only these fields can be emitted:

- `timestamp`
- `severity`
- `component`
- `eventCode`
- `requestId`
- `durationMs`
- `statusCode`
- `resourceKind`
- `resourceKey`

Optional empty fields are omitted. Components, event codes, request IDs, and resource kinds are syntactically validated. Resource IDs are never written directly: validated IDs such as a peer IP are SHA-256 hashed into a bounded `resourceKey` before output.

Current events cover application lifecycle, configuration reload outcomes, completed HTTP requests, cancelled HTTP requests, and recovered panics. Event records intentionally cannot accept arbitrary message strings or error objects.

## Privacy and failure handling

The logger has no fields for request/response bodies, headers, tokens, environment variables, filesystem paths, raw client addresses, container logs, or exported data. Panic values and stack traces are not returned or logged. API panics that occur before a response starts become a generic versioned `500` error; non-API panics become generic plain text.

If a client cancels a request, the completion event is emitted at warning severity with `http.request.cancelled`. Durations are clamped to zero if a faulty or test clock moves backward.

The application cannot publish its own liveness response after the process or listener has stopped. External process supervision, journal retention, restart policy, and alert delivery belong to later deployment and monitoring tasks.
